# PantryAI — 재료명 정규화 파일럿 (2단계 정제) 작업 지시

> 이 파일을 별도 세션에 그대로 붙여넣는다. BMAD는 로드하지 않는다.

---

## ⚠️ 먼저 읽을 것 — 이 작업은 측정 대상이다

이 작업의 결과는 **정답 세트와 대조해 일치율로 채점된다.** 그래서 다음 파일을 **절대 열지 않는다.**

| 열지 말 것 | 이유 |
| --- | --- |
| `data/labels/ingredient_standard_answers.csv` | **정답지다.** 보면 측정이 무의미해진다 |
| `data/labels/archive/ingredient_standard_raw.csv` | 위 파일의 이전 버전 |
| `data/labels/ingredient_dictionary_draft.csv` | 규칙이 만든 부분 정답. 파일럿에서는 쓰지 않는다 |
| `scripts/score_normalization.py` | 채점 스크립트. 채점은 이 세션이 하지 않는다 |

**채점도 하지 않는다.** 산출물만 만들고 끝낸다. 채점은 분리된 시점에 수행한다 —
지금 채점하면 결과를 보고 프롬프트를 고치게 되고, 그 순간 측정이 오염된다.

실수로 열었다면 **숨기지 말고 보고한다.** 오염된 수치를 모르고 쓰는 것이 훨씬 나쁘다.

---

## 배경

PantryAI는 사용자의 냉장고 재고를 기준으로 요리를 추천하는 서비스다.
레시피 코퍼스는 두 공공 API에서 수집해 1단계 정제를 마쳤다 — 두 소스가 같은 스키마로 통합돼 있다.

그런데 **재료명이 원본 표기 그대로다.** 같은 재료가 여러 이름으로 흩어져 있다.

```
마늘 347행 · 다진마늘 282행 · 다진 마늘 151행 · 마늘다진것 36행 · 통마늘 11행
달걀 168행 · 계란 111행
```

사용자가 재고에 `마늘`을 넣었을 때 `다진마늘`을 요구하는 레시피가 매칭되지 않으면
추천이 통째로 사라진다. **이 작업은 각 재료 행에 표준명을 배정하는 것이다.**

수행 시점은 **빌드 시점 일괄 배치**로 확정돼 있다(결정 D-029). 실행 시점에 도는 작업이 아니므로
레시피 맥락(요리명·조리과정)을 함께 보고 판단해도 된다 — 오히려 그러라고 이 시점을 골랐다.

## 입력 파일

| 파일 | 내용 |
| --- | --- |
| `data/processed/recipe_ingredients.json` | 재료 18,988행. `source` `source_id` `seq` `name_raw` `qty_raw` `role_raw` `group_name` |
| `data/processed/recipes.json` | 레시피 1,693건. 요리명·분류·인분 등 |
| `data/processed/recipe_steps.json` | 조리과정 9,587단계. `step_no` `description` |
| **`data/labels/standard_names.txt`** | **목표 어휘 349종.** 이 목록 밖의 이름을 만들지 않는다 |
| **`data/labels/README.md`** | **정규화 규칙.** 사람이 정답 세트를 만들 때 따른 것과 같은 규칙이다 |
| `data/labels/pilot_recipes.txt` | 이번 파일럿 대상 50건 (`source<TAB>source_id`) |

`data/raw/`는 읽지 않는다. 1단계 산출물만 쓴다.

## 작업 범위

`pilot_recipes.txt`에 있는 **50건**(농정원 16 + 식약처 34)의 재료 행 **582행**에만 표준명을 배정한다.
전량(18,988행)은 파일럿 결과를 검토한 뒤에 돌린다.

표집은 소스별 `source_id` 정렬 후 균등 간격으로 뽑은 것이라 **무작위가 아니고 재현 가능하다.**

## 정규화 규칙

**`data/labels/README.md`를 읽고 그대로 따른다.** 여기 요약을 옮기지만, 충돌하면 README가 우선한다.

핵심 판정 기준은 하나다.

> **재고에 A가 있을 때, B를 요구하는 레시피를 실제로 만들 수 있는가?**

| 축 | 처리 |
| --- | --- |
| 가공 상태 (다진·채썬·즙·간 것) | **통합** — 사용자가 직접 할 수 있다 |
| 부위 (등심·안심) | **통합** — 가정에서 구분하지 않는다 |
| 품종 (대파/실파, 표고/팽이, 홍고추/청양고추) | **구분** — 만들어낼 수 없다 |
| 건조 (생표고/말린표고) | **구분** — 되돌릴 수 없고 맛·용도가 바뀐다 |
| 조리 단계 차이 | **통합** |
| 결과물이 달라지는 차이 (화이트와인/레드와인) | **구분** |

판단이 애매하면 **같은 레시피에 두 이름이 함께 나오는지** 본다. 함께 나오면 작성자가 구분했다는 뜻이다.
다만 **함께 안 나온다고 같은 물건은 아니다** — 한 요리에 두 종류의 김치를 넣을 일이 없어 0이 나올 뿐이다.

### 어휘 제약

**`standard_names.txt`의 349종 안에서만 고른다.** 목록에 마땅한 이름이 없으면
`name_raw`를 그대로 표준명으로 쓰고 `근거`에 `어휘없음`이라고 적는다. **새 이름을 지어내지 않는다.**

### 맥락을 봐야 하는 경우

일부 재료명은 이름만으로 결정할 수 없다. 예를 들어 `치즈 2장`은 조리과정을 읽어야 종류를 알 수 있다.
**요리명과 조리과정을 근거로 판단하고, `근거` 컬럼에 무엇을 보고 정했는지 적는다.**
판단이 안 되면 추측하지 말고 `근거`에 `판별불가`라고 적는다 — 억지 배정보다 낫다.

## 하지 말 것

- **정답 세트를 열지 않는다** (위 표 참조)
- **채점하지 않는다.** 일치율을 계산하려 시도하지 않는다
- `name_raw`를 수정하지 않는다 — 원본 표기는 보존한다
- `data/processed/`의 어떤 파일도 수정하지 않는다
- 어휘 밖의 표준명을 만들지 않는다
- 재료 행을 추가·삭제·병합하지 않는다
- 수량(`qty_raw`)을 해석하거나 단위를 통일하지 않는다 — 이 작업 범위가 아니다
- 카테고리 분류·주재료 판정·중복 레시피 판정을 하지 않는다 — 별도 단계다

## 검증 요구사항

산출물을 쓰기 전에 스스로 확인하고, 결과를 대화로 보고한다.

| 검사 | 기준 |
| --- | --- |
| 행 수 | 입력 582행 == 출력 582행 |
| 키 보존 | `(source, source_id, seq)` 조합이 입력과 정확히 일치 |
| `name_raw` 보존 | 입력과 문자열이 완전히 같다 |
| 어휘 준수 | `표준명`이 전부 `standard_names.txt` 안에 있다 (`어휘없음` 표시분 제외) |
| 공란 | `표준명`·`근거` 공란 0 |

**어긋나면 파일을 쓰지 말고 멈춘다.** 이 프로젝트의 1단계 파이프라인도 같은 규칙을 쓴다
(`build_processed.py`는 행 수 잔차가 0이 아니면 산출물을 쓰지 않고 멈춘다).

## 함께 보고할 것

산출물과 별개로, 대화에서 다음을 알려준다. **이게 파일럿의 진짜 목적이다.**

1. **판별불가로 남긴 행** — 몇 행이고 어떤 재료명인가
2. **어휘없음으로 남긴 행** — 349종에 마땅한 이름이 없었던 경우
3. **규칙이 모호했던 지점** — README를 읽고도 갈렸던 케이스. 규칙을 고칠 재료가 된다
4. **맥락(조리과정)이 실제로 판단을 바꾼 횟수** — 이름만 봤을 때와 다른 답이 나온 경우.
   이 수치가 "레시피 단위로 묶어 호출한다"는 설계 결정(D-029)의 근거가 맞는지 검증한다
5. **레시피당 평균 투입 토큰** — 전량(1,693건) 확대 시 비용 추정에 쓴다

---

## 작업 방식

1. `data/labels/README.md`와 `standard_names.txt`를 먼저 읽는다
2. `pilot_recipes.txt`의 50건에 해당하는 재료·조리과정을 모은다
3. **레시피 단위로** 판단한다 — 재료 목록과 조리과정을 함께 놓고 본다
4. 검증 5항목을 통과하면 `data/labels/stage2_pilot_output.csv`를 쓴다
5. 위 5가지를 보고한다

작업이 길어지면 중간 산출물을 파일로 남기고 이어서 한다.
**결과를 좋게 만들려고 규칙을 바꾸지 않는다** — 규칙이 이상하면 그 사실을 보고한다.
