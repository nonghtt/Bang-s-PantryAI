# PantryAI — 원천 데이터 1단계 정제 작업 지시

> 이 파일을 별도 구현 세션에 그대로 붙여넣는다. BMAD는 로드하지 않는다.

## 배경

PantryAI는 사용자의 냉장고 재고를 기준으로 요리를 추천하는 서비스다. 레시피 코퍼스를 두 공공 API에서 전수 수집해 `data/raw/`에 보존해 두었다. 이 원천 데이터는 두 소스의 구조가 완전히 달라 그대로는 DB에 넣을 수 없다.

**이 작업은 두 소스를 같은 모양으로 맞추는 것까지만 한다.** 판단이 들어가는 작업(재료명 표준화, 주재료 판정, 카테고리 분류, 중복 레시피 판정, 데이터 생성)은 **전부 다음 단계이며 여기서 하지 않는다.**

## 소스별 변환 규칙

### 농정원

**1. 3개 파일을 `RECIPE_ID`로 결합한다.**

**2. 고아 레시피 38건을 분리 보존한다.**
`ingredient`에는 등장하지만 `basic`에 없는 `RECIPE_ID`가 38개 있다(불린 쌀 기반 이유식·죽 계열). **삭제하지 말고** `data/processed/orphans/`에 따로 내보낸다. 처리 방침은 다음 단계에서 정한다.

**3. 재료명에 섞인 대괄호 그룹 헤더를 분리한다.** (16종 / 19행)

```
'[쇠고기양념] 다진파'  →  group_name '쇠고기양념',  name_raw '다진파'
'[절임용 소금물] 소금'  →  group_name '절임용 소금물', name_raw '소금'
```

**4. 한 칸에 여러 재료가 들어간 행을 분해한다.** (8종)

```
'식용유/소금/참기름/잣가루'       → 4행
'빨강파프리카·노랑 파프리카·청피망'  → 3행
'후추, 식용유'                  → 2행
'무,래디쉬'                    → 2행
'홍피망, 청피망 각각'            → 2행 ('각각'은 버린다)
'노랑/빨강 파프리카'             → 2행 ('노랑 파프리카', '빨강 파프리카')
'굵은소금·후춧가루'              → 2행
'소금, 후추'                   → 2행
```
분해 시 `qty_raw`는 원본 값을 복제한다.

**5. 명백한 오탈자만 교정한다.** 아래 목록 외에는 손대지 않는다.

```
돼기고기   → 돼지고기   (6행)
고추가루   → 고춧가루   (6행)
다진생각   → 다진생강   (1행)
다진식파   → 다진실파   (1행)
```

**6. 재료명의 앞뒤 공백을 제거한다.** 단 **내부 공백은 그대로 둔다** — `다진 마늘`을 `다진마늘`로 붙이는 것은 표준화이므로 다음 단계다.

**7. 코드 컬럼을 버린다.** `ROW_NUM` `NATION_CODE` `TY_CODE` `IRDNT_CODE` `IRDNT_TY_CODE` `IRDNT_SN`(seq로 대체)

> **주의**: 수집분에 `IMG_URL`·`DET_URL` 컬럼이 존재하지 않는다. API 명세에는 있으나 수집 데이터에 없으므로 농정원 레시피에는 이미지가 없다. 이 사실을 결과 보고서에 기록한다.

### 식약처

**8. `RCP_PARTS_DTLS` 문자열을 재료 행으로 분해한다.** 이것이 이 작업의 핵심이자 가장 어려운 부분이다.

관측된 구조 (1,156건 기준):
- 개행(`\n`) 포함 **670건 (58.0%)**
- 콜론(`:`) 포함 **329건** — 그룹 헤더 구분자
- 대괄호(`[`) 포함 **150건**
- 유니코드 분수(`½⅓¼⅔`) 포함 **60건**
- `●` 불릿 **38건**, `<br>` 태그 **27건**, `·` 불릿 **2건**
- 빈 문자열 **3건**
- 평균 114자, 최대 285자

실제 형태 예시:

```
(a) 첫 줄이 요리명, 그 다음이 재료
    '새우두부계란찜\n연두부 75g(3/4모), 칵테일새우 20g(5마리), 달걀 30g(1/2개)\n고명\n시금치 10g(3줄기)'

(b) 인분 표기가 앞에 붙음 + 불릿 그룹 헤더
    '[1인분]조선부추 50g, 날콩가루 7g(1⅓작은술)\n·양념장 : 저염간장 3g(2/3작은술), 다진 대파 5g(1작은술)'

(c) ● 그룹 헤더 + 콜론
    '●방울토마토 소박이 : \n방울토마토 150g(5개), 양파 10g(3×1cm)\n●양념장 : \n고춧가루 4g(1작은술)'

(d) 대괄호 그룹 + HTML 태그
    '2인분 기준<br>\n•[간편식 재료] 알배추(40g), 우목심(50g)<br>\n\n•[추가 재료] 오징어(30g), 새우(40g)'

(e) 수량이 괄호 안에 오는 형태
    '[ 2인분 ] 팽이버섯(½봉), 느타리버섯(½줌), 소고기(불고기용 부채살, 200g), 소금(0.3Ts)'

(f) 문장 중간의 인라인 그룹 헤더
    '... 식용유 1g [소스소개] 저나트륨간장소스:간장 1g, 물 2g, 설탕 1g, 식초 1g'
```

처리 순서 제안:
1. `<br>` 태그를 개행으로 치환
2. 앞머리의 인분 표기(`[1인분]` `[ 2인분 ]` `2인분 기준`)를 떼어 `servings_raw`에 보관
3. `●` `•` `·` 불릿과 대괄호 그룹 헤더를 그룹 경계로 인식
4. 콜론 앞부분을 `group_name`으로, 뒷부분을 재료 목록으로 분리
5. 쉼표와 개행으로 재료 항목 분해
6. 각 항목을 `재료명` + `수량표기`로 분리
   - `연두부 75g(3/4모)` → 이름 `연두부`, 수량 `75g(3/4모)`
   - `팽이버섯(½봉)` → 이름 `팽이버섯`, 수량 `½봉`
   - `소고기(불고기용 부채살, 200g)` → 이름 `소고기`, 수량 `불고기용 부채살, 200g`
   - `물(4컵=800g)` → 이름 `물`, 수량 `4컵=800g`
7. 재료명이 아닌 항목(요리명, `고명` 같은 섹션 라벨)은 버리지 말고 `group_name`으로 흡수하거나 별도 표시

**규칙만으로 100% 처리되지 않는다.** 정규식으로 처리되지 않는 항목은 버리지 말고 `data/processed/unparsed_ingredients.json`에 원본과 함께 남긴다. LLM 파싱은 다음 단계에서 이 잔여분에 적용한다.

**9. `MANUAL01`~`MANUAL20`을 조리 단계 행으로 편다.**
빈 문자열 컬럼은 행을 만들지 않는다. `MANUAL_IMG01`~`20`을 같은 순번의 `image_url`로 붙인다.
단계 수 분포: 6단계 1,048건(90.7%) · 5단계 52 · 3단계 51 · 4단계 4 · 0단계 1.
설명 앞의 `"1. "` `"2. "` 번호 접두어는 제거하고 `step_no`로 옮긴다.

**10. 코드/불필요 컬럼을 버린다.** `RCP_SEQ`는 `source_id`로 보존한다.

## 하지 말 것

아래는 전부 **다음 단계**다. 이 작업에서 손대면 되돌릴 수 없는 정보 손실이 생긴다.

| 하지 말 것 | 이유 |
| --- | --- |
| 재료명 표준화 (`다진마늘`→`마늘`, `달걀`→`계란`) | 접는 기준이 별도로 확정되어 있고, LLM이 수행한다 |
| 주재료/부재료 판정 | 판정 기준 미정. 식약처엔 필드 자체가 없다 |
| 카테고리(한식/양식/중식/일식/동남아) 부여 | 키워드 방식으로는 오분류가 실증되었다 |
| 중복 레시피 삭제 | 이름이 같아도 다른 레시피다. 아래 근거 참조 |
| 고아 레시피 38건 삭제 | 분리 보존만 한다 |
| 데이터 생성·보강 | 다음 단계 |
| 수량 단위 환산 (`1큰술`→`15ml`) | 재고는 유무만 관리하므로 애초에 불필요할 수 있다 |

**중복 삭제 금지의 근거** — 두 소스에 이름이 완전히 같은 레시피가 14건 있으나(`잡채` `닭강정` `안심스테이크` `연어샐러드` `전복죽` 등), 실제로 열어보면 다른 레시피다.

```
농정원 잡채   쇠고기 100g · 느타리버섯 800g · 배 · 오이 · 당근      625Kcal
식약처 잡채   등심 20g · 표고 10g · 도라지 · 호부추 · 달걀         197.7Kcal
```

## 검증 요구사항

작업 후 `data/processed/report.md`에 아래를 남긴다. **입력 건수와 출력 건수가 잔차 0으로 대조되어야 한다.**

1. **행 수 대조** — 소스별로 `입력 행수 = 출력 행수 + 분해로 늘어난 행수 - 명시적으로 제외한 행수`. 제외한 행은 사유와 함께 전량 나열한다.
2. **레시피 건수** — 농정원 537 + 식약처 1,156 = 1,693. 고아 38건은 별도 집계.
3. **식약처 파싱 성공률** — 1,156건 중 몇 건이 재료 행으로 분해되었는가. 실패분은 `unparsed_ingredients.json`의 건수와 일치해야 한다.
4. **식약처 재료 행 수** — 분해 결과 총 몇 행인가. (참고: 농정원은 6,104행 / 레시피당 평균 10.6개)
5. **분해로 늘어난 행** — 농정원 복수 재료 분해 8종이 몇 행으로 늘었는가.
6. **오탈자 교정 건수** — 4종 각각 몇 행을 고쳤는가.
7. **빈 값 현황** — 소스별로 어떤 필드가 얼마나 비어 있는가.

## 참고 — 알려진 원천 데이터 결함 (고치지 말고 기록만)

- **식약처 일부 레시피는 재료 목록과 조리법이 서로 다른 요리다.** 조리과정에만 등장하고 재료 목록엔 없는 재료가 3종 이상인 레시피가 근사 측정으로 21건(1.8%). 예: `잡채`(조리법이 양배추·깻잎·상추·배·겨자를 요구하나 재료 목록에 없음), `두부 카프리제`(재료 목록에 두부가 없음), `새콤한연어샐러드`. **판정·수정하지 말고 목록만 뽑아 보고서에 남긴다.**
- 농정원 `IRDNT_CPCTY`의 18.4%가 `약간`·`적당량`으로 수치가 아니다.
- 농정원 `느타리버섯 800g`(4인분 잡채) 같은 수량 이상치가 있다. 고치지 않는다.

## 작업 방식

- Python으로 수행한다. 이 환경에는 `uv`가 없고 `python`(3.14.3)을 직접 쓴다.
- 콘솔 인코딩 문제를 피하려면 `PYTHONIOENCODING=utf-8`을 설정한다.
- 변환 스크립트를 `scripts/` 아래에 남긴다. **재실행 가능해야 한다** — 원천 파일에서 산출물까지 한 번에 다시 만들 수 있어야 한다.
- `data/raw/`는 읽기 전용으로 취급한다. 절대 수정하지 않는다.
