# Addendum — 브리프에 담기엔 상세하지만 버리면 안 되는 것

브리프는 1~2쪽으로 유지한다. 이 문서는 **PRD·아키텍처가 실제로 쓸 재료**를 담는다.

---

## 1. API 접속 규격 (아키텍처·구현 직결)

### 농정원 — 농림축산식품 공공데이터 포털 경유

```
http://211.237.50.150:7080/openapi/{API_KEY}/{json|xml}/{GRID_ID}/{START}/{END}
```

| Grid ID | 내용 | 건수 | data.go.kr 데이터셋 |
| --- | --- | ---: | --- |
| `Grid_20150827000000000226_1` | 레시피 기본정보 | 537 | 15057205 |
| `Grid_20150827000000000227_1` | 레시피 재료정보 | 6,104 | 15058981 |
| `Grid_20150827000000000228_1` | 레시피 과정정보 | 3,022 | 15056535 |

- 인증키는 **data.go.kr 계정당 1개**, 활용신청한 API 전체에 공통
- 응답 구조: `{GRID_ID}.totalCnt` / `.result.code` / `.row[]`
- 정상 코드 `INFO-000`, 미신청 `INFO-100`, 없는 서비스 `ERROR-310`
- 1회 최대 1,000건. 전수 수집은 500건 단위 페이징으로 처리했다
- **서버 IP 등록이 필요하다.** 다만 우리 설계는 런타임에 공공 API를 호출하지 않고 **1회성 배치로 수집해 자체 DB에 적재**하므로, 수집하는 개발 PC 한 대만 등록하면 된다. 배포 서버 IP는 불필요하며, 이 덕분에 고정 IP가 없는 서버리스 배포도 막히지 않는다

### 식약처 — 식품안전나라 직접

```
http://openapi.foodsafetykorea.go.kr/api/{KEY}/COOKRCP01/json/{START}/{END}
```

**data.go.kr 인증키로는 동작하지 않는다** (`INFO-100`). 식품안전나라에서 별도 발급받아야 한다.

주요 필드: `RCP_SEQ` `RCP_NM` `RCP_WAY2`(조리방법) `RCP_PAT2`(요리종류) `INFO_ENG/CAR/PRO/FAT/NA`(영양 5종) `RCP_PARTS_DTLS`(재료 문자열) `MANUAL01~20`+`MANUAL_IMG01~20`(조리 20단계) `HASH_TAG`

- `RCP_PAT2` 실제 값: 밥 / 국·찌개 / 반찬 / 후식
- `RCP_WAY2` 실제 값: 끓이기 / 찌기 / 굽기 / 튀기기 / 기타
- 재료는 **비정형 문자열**: `"연두부 75g(3/4모), 칵테일새우 20g(5마리), …"` — 파싱 필요

### 영양 확장용 (Vision 단계)

농촌진흥청 **농식품올바로** OpenAPI — 국가표준식품성분표. 영양 심화 기능을 되살릴 때의 소스.

## 2. 재료 데이터 상세 (온톨로지 설계 재료)

### 상위 재료 빈도 (6,104행 기준)

```
소금 340 · 설탕 217 · 참기름 208 · 다진마늘 206 · 간장 192 · 후춧가루 181
물 173 · 양파 148 · 깨소금 135 · 대파 126 · 고춧가루 116 · 다진파 109
당근 107 · 홍고추 97 · 마늘 95 · 식용유 92 · 계란 88 · 쇠고기 88
청고추 73 · 식초 73 · 고추장 69 · 무 60 · 오이 59 · 생강 59 · 실파 58
표고버섯 56 · 두부 56 · 밀가루 55 · 청주 47 · 밥 45
```

### 정규화가 필요한 패턴

| 패턴 | 사례 |
| --- | --- |
| **가공 상태가 이름에 결합** | `마늘`(95) ↔ `다진마늘`(206) / `파` 계열 → `대파`(126)·`다진파`(109)·`실파`(58) |
| **등급·종류 변형** | `간장`(192) ↔ `진간장`(38) |
| **표기 흔들림** | `계란`(88) — 식약처는 `달걀` 표기 |

→ **"재료 본체 + 가공 상태"로 분해하는 것이 정규화의 뼈대.** 재고에 "마늘"이 있으면 "다진마늘"을 요구하는 레시피도 매칭되어야 한다.

### 용량 표기 분포 (고유 382종)

```
약간 1051(17.2%) · 1큰술 506 · 2큰술 307 · 1개 304 · 1작은술 215
1/2개 197 · 3큰술 164 · 100g 141 · 50g 125 · 2개 121 · 1/2큰술 119
30g 98 · 1컵 93 · 20g 90 · 1/4개 84 · 10g 84 · 200g 79 · 1/2컵 74
… 적당량 49 · 1뿌리 53 · 1마리 48
```

**세 계통이 섞여 있다**: 정량(g·ml) / 계량도구(큰술·작은술·컵) / 개수·단위(개·뿌리·마리) / **비정량(약간·적당량, 약 18%)**.

비정량 표기는 대부분 양념류이므로 `IRDNT_TY_NM = 양념` 필터로 흡수된다. 정밀도 층위 분리가 여기서도 값을 한다.

### 레시피당 재료 개수

평균 **10.6개**. 분포는 5~15개 구간에 집중되며 최소 2개, 최대 20개.

## 3. 커버리지 측정 방법론 (재현용)

### 재고 가정 — 상비 재료 21종

**재료에는 두 종류가 있다.** 늘 있는 **상비 재료**와, 특정 요리를 하려고 사는 **목적 구매 재료**다. 둘을 섞으면 커버리지가 실제보다 높게 나온다.

```
[상비 17종]  쌀 계란 김치 김 양파 대파 마늘 우유
             간장 고추장 된장 소금 설탕 식용유 참기름 고춧가루 후추
[자주 4종]   감자 당근 두부 돼지고기
```

**제외한 것**(목적 구매): 콩나물 · 시금치 · 애호박 · 어묵 · 참치 · 버섯 · 닭고기 · 고추

> 초기 30종 목록에는 목적 구매 재료(어묵·참치·콩나물 등)가 섞여 있었다. **상비 여부는 레시피 등장 빈도가 아니라 실제 보유 여부로 판단해야 한다** — 후추는 레시피에 주재료로 5번밖에 안 나오지만 누구나 갖고 있다.

### 측정 규칙

`IRDNT_TY_NM = 양념`인 행과 **이름이 양념류인 항목**(밀가루·버터·녹말·육수 등)을 제외한 주재료·부재료만 대상으로, 재고에 없는 재료 수를 센다. 0개면 완전 매칭, 1개면 **보완 재료 제안 대상**.

식약처는 `IRDNT_TY_NM`이 없고 재료가 비정형 문자열이므로 정규식으로 근사 파싱했다.

### 측정 결과 (기준선)

| 코퍼스 | 건수 | 완전 매칭 | 1개 부족 | 도달 가능 |
| --- | ---: | ---: | ---: | ---: |
| 농정원 | 573 | 11 | 77 | **15.4%** |
| 식약처 (근사) | 1,152 | 5 | 34 | **3.4%** |
| **병합** | **1,725** | **16** | **111** | **7.4%** |

**식약처를 1,156건 넣어도 1개 부족은 34건만 늘었다(효율 2.9%).** 레시피당 재료가 농정원 4.9개 대비 7.8개로 많고 나트륨 저감 건강식이라 재료가 특이하기 때문이다. **코퍼스를 무작정 키우는 것보다 재고 제약 조건부 생성이 훨씬 효율적이라는 데이터 근거.**

### 알려진 한계

- 매칭이 단순 부분문자열이라 `대파`/`실파`, `계란`/`달걀`을 다른 재료로 센다 (과소 추정)
- 반대로 `버섯`·`고추` 같은 상위어는 하위 항목을 전부 잡는다 (과대 추정) — 현재 목록에서는 둘 다 제외했다
- `IRDNT_TY_NM`이 레시피마다 일관되지 않는다 — **소금이 양념으로 416건, 주/부재료로 70건**에 나타난다. 필드만 믿을 수 없어 이름 기반 필터를 병행했다
- 식약처 파싱이 정규식 기반 근사치다

**정규화 이후 재측정하면 수치가 오른다.** 정규화 효과를 정량화하는 지점이므로 위 기준선을 보존한다.

### 부수 결과 — 보완 재료 제안 알고리즘 사전 검증

"하나만 사면 열리는 레시피 수" 상위(병합 기준): **쇠고기 5 · 깻잎 5 · 단호박 5 · 오징어 4 · 청고추 4 · 시금치 4 · 닭 3 · 가지 3**. 기능이 실제 데이터에서 유의미한 결과를 낸다는 증거.

## 4. 데이터 소스 배제 근거 (상세)

### 만개의레시피 — KADX 농식품 빅데이터 거래소

10만 건 이상으로 규모가 압도적이었고, 크롤링이 아니라 **거래소를 통한 정식 확보 경로**가 존재했다. 그러나 상품 페이지에서 확인한 실제 라이선스가 **CC BY-NC-ND**였다.

- **ND(변경금지)가 결정적**이다. 이 프로젝트의 1번 작업이 LLM 기반 재료 파싱·정규화·임베딩인데, 그것이 곧 2차 저작물 생성이다
- NC(비영리)도 취업용 포트폴리오의 공개 배포에서 해석 다툼 여지가 있다
- 참고: KADX는 판매회원이 상품별로 조건을 정하는 마켓플레이스라 **단일 라이선스 답이 없다.** 상품마다 개별 확인이 필요하다

### TheMealDB

무료·오픈 데이터로 조건이 가장 깨끗해 보였고 `Area` 필드로 국가 분류를 제공한다. 그러나:

- **다중 재료 필터링이 Premium 전용** — 이 제품의 핵심 질의가 정확히 다중 재료 검색이다
- 개발 키(`1`)는 개발·교육용 한정이며 **공개 배포 서비스는 프로덕션/Premium 키 필요**
- 스크래핑 금지, **재료·조리법의 임의 변경·추가 금지**, API 재판매 금지
- 출처 표기 의무: `Recipe data and imagery: TheMealDB (https://www.themealdb.com/)`

### 일반화된 교훈

> **상용 레시피 API는 호출 과금이 비즈니스 모델이라 구조적으로 벌크 다운로드와 자체 저장을 허용하지 않는다. 그런데 RAG 코퍼스는 데이터 소유를 전제한다. 이 둘은 원리적으로 충돌한다.**

Spoonacular·Edamam도 같은 결론일 가능성이 높다. 검토한다면 "상업 이용 가능" 문구가 아니라 **응답 데이터의 저장·캐싱 조항**을 먼저 봐야 한다.

### RecipeNLG

223만 건이지만 **비상업 연구·교육 목적 한정**. 공개 배포 시 회색지대이므로 배제.

### 국외 데이터의 비(非)라이선스 장애물

자취생 재고는 대파·김치·두부·계란인데 영문 레시피는 buttermilk·cilantro·cheddar·bacon을 요구한다. **번역해도 재고 매칭이 안 된다.** 재료 온톨로지가 두 배로 복잡해지고 "매칭은 됐는데 구할 수 없는" 추천이 나온다. 라이선스가 깨끗하더라도 전체 코퍼스를 국외로 부풀리는 것은 역효과다.

## 5. 기술 선택의 배경 — 지원자 강점·공백 지도

`korea-doc/프로필/career.md`·`personal.md` 대조 결과. **기술 선택의 근거이므로 남긴다.**

### 이 프로젝트가 메워야 할 공백

| 공백 | 근거 |
| --- | --- |
| **RAG 직접 구축** | flow-counsel에서 RAG를 *연동*만 했고, career.md에 "RAG 검색 엔진 자체는 외부 제품 기능"이라 경계를 명시해 두었다. 청킹·임베딩·리트리버·리랭킹 설계 경험이 없다 |
| **React** | Vue3 전용. 서류 필터에서 걸리는 항목이라 React 고정은 정당한 선택이다 |
| **공개된 실서비스** | 업무는 전부 고객사 발주(비공개), 개인 프로젝트는 CLI 도구. **면접관이 열어볼 수 있는 것이 없다** |
| **인프라 설계·배포** | AWS는 gs-retail에서 *이관 검증*만 담당했고 설계·수행은 범위 밖이었다 |

### 이미 증명된 것 — 중복 투자를 피할 영역

`[취업준비자동화]`에서 **서브에이전트 오케스트레이션 · 검증(반박) 에이전트 · 출처 추적 · 원문 확인/미확인 구분**을 이미 구현했다. 에이전트 하네스는 신규 학습이 아니라 **CLI에서 웹 제품으로 이식하는 것**으로 포지셔닝한다.

### 서명 강점 — 차별화가 나오는 자리

성능 최적화(1,400ms→10ms) · 동시성/정합성(Deadlock·비관적 락·after-commit) · **관측 기반 진단**(원인이 안 보이면 로깅부터 심는다) · **잔차 0까지 대조하는 정밀함**(2,040건을 1,960/74/6으로 분해).

> LLM 프로젝트의 대다수가 "돌아간다"에서 멈춘다. **"얼마나 정확한지 수치로 증명한다"** 를 할 수 있는 것이 이 프로젝트의 차별점이며, `Success Criteria`의 네 지표가 그 실행 계획이다.

### 실무 강점을 사용자 없이 증명하는 방법

농림부에서 **150만 건 시드 데이터로 부하를 검증**한 전례가 있다. 같은 수법을 적용해 레시피·가상 사용자 재고 이력을 시딩하면 "사용자가 없어서 성능을 말할 수 없다"는 변명이 필요 없어진다.

## 6. 아키텍처로 넘기는 갈림길

### 백엔드 스택

| 선택지 | 얻는 것 | 잃는 것 |
| --- | --- | --- |
| **Spring Boot** | 지원자 최대 강점(JPA·동시성·성능·정합성)을 그대로 전시. 실무 연속성 | LLM 생태계 라이브러리가 빈약 |
| **Python / FastAPI** | LLM·임베딩·벡터DB 생태계에 바로 붙음 | 강점 영역을 보여줄 무대가 줄어듦 |
| **하이브리드** | 주 API는 Spring, AI 서비스는 Python | 사이드 프로젝트에 운영 복잡도 |

**단순 취향이 아니라 "무엇을 증명할지"에 따라 답이 갈린다.** 아키텍처 단계의 첫 결정.

### 그 밖에

- RAG 청킹 전략과 임베딩 모델 선택
- 벡터DB (자체 호스팅 vs 관리형)
- React 상태관리 및 스트리밍 UI 처리
- 배포 대상 (서버리스 가능 여부는 §1의 IP 제약과 무관하므로 열려 있다)

## 7. 세션 운영 메모

- 기획 세션과 구현 세션을 분리한다. BMAD와 superpowers 스킬이 모두 로드된 상태에서 섞으면 컨텍스트가 빨리 오염된다
- BMAD는 **에픽·스토리 분해까지** 사용하고 이후 제거한다. 산출물은 `docs/`로 **요약 없이 원문 이동** — 요약하면 결정의 근거가 사라진다
- 환경: `uv` 미설치로 BMAD 스크립트는 `python`으로 직접 실행 중 (Python 3.14.3)
